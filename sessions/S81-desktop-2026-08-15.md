## §5 The design, before it is built

**Why this is not simply "time the loop."** S80 deliberately did not measure speed, because a
single wall-clock number conflates four different costs: model load, prompt processing, token
generation, and transport. S79's `+27 %` is unbankable partly because nobody can now say which of
those four it described. The arm therefore reports the components separately, using the names the
field already uses, and refuses to print a rate whose denominator it did not observe.

**The vocabulary is the deliverable, not a by-product.** `docs/34` fixes it; the harness is its
first consumer and prints in it; the manual carries it for the operator. If the three ever
disagree, the harness is wrong — a document may describe an instrument, but the instrument may
not invent a word the document does not define.

**What "matches the world" means concretely:** prefill/decode split as in llama.cpp's `pp`/`tg`
and Ollama's `prompt_eval_*`/`eval_*`; TTFT and TPOT as in the serving literature; p50/p95 rather
than a bare mean; cold and warm never mixed in one number; a speedup always printed as the two
measurements it divides.

### §6.4 The finding that reframes the migration

`Observed` — **Ollama 0.32.13 runs `llama-server` as its own inference engine**
(`AppData\Local\Programs\Ollama\lib\ollama\llama-server.exe`, parent `ollama serve`; seen in the
process tree while diagnosing §10.4). "Ollama vs llama.cpp" is therefore **not engine versus
engine — it is one engine under two sets of flags**:

| | Ollama's invocation | ours |
|---|---|---|
| batch / ubatch | `-b 1024 -ub 1024` | defaults (`-b 2048 -ub 512`) |
| template | `--no-jinja --chat-template chatml` | `--jinja` |
| flash attention | `auto` | `on` |
| context | `-c 8192 --context-shift --keep 4` | `-c 8192` |

The micro-batch difference is the leading candidate for the 0.81× prefill gap — **a hypothesis
with an experiment attached, not a conclusion.** It also means the migration's premise needs
restating before it is worth pursuing: the question is not "is llama.cpp faster than Ollama" but
"which flags, on the one engine, and what does bypassing Ollama actually buy."

## §10 Known Failures — mine, first-class

**The pattern of this session: I wrote the document that names a trap, then walked into that trap
three times while building the instrument meant to obey it.** docs/32 §6 predicts the next defect
appears in whatever is built to enforce a rule. Three for three.

**10.1 The harness warmed up on a chunk it then measured.** Prefill came back **37,729 tok/s**
against 4,801 for the next chunk — the instrument timing its own warmup. docs/34 §4 warned about
cached prefill in the abstract before this was written. Fixed: the warmup uses an unmeasured chunk.

**10.2 The second llama.cpp arm re-sent the first arm's exact prompts** and was handed 524 and
1,166 tokens free, reporting `prompt_n = 1` — a rate that is arithmetically correct and describes
a one-token prefill. Fixed: `"cache_prompt": false`, plus any prefill whose prompt was >20 %
cached is **withheld**, not footnoted.

**10.3 And then the same trap a third time, where the guard could not see it.** A previous run's
Ollama engine was still resident, so the run took its VRAM "baseline" at **7,323 MiB with a model
loaded** — making its own unload check pass trivially — and reported prefill at **61,093 / 63,619
/ 65,393 tok/s** on a card that does ~4,000–6,000. Ollama exposes **no** cache field, so the 20 %
guard was blind exactly where the danger was unseeable. Fixed structurally (unload before the
baseline, so the cache is empty by construction) and empirically (the warmup, following a
proven-cold card, becomes the run's measured reference; anything >3× it is withheld). Both rules
were written into docs/34 and ch.18 **after** being paid for.

**10.4 I gave Rab a confident wrong diagnosis.** Mid-run I reported the measurement "healthy, in
the slow thinking arm at 94 % GPU." It was not: it never left the Ollama arm and was hung. I had
seen a process named `llama-server` at 94 % and concluded it was my llama.cpp arm — it was
**Ollama's own engine** (`AppData\Local\Programs\Ollama\lib\ollama\llama-server.exe`, parent
`ollama serve`). A name matched, and I read it as an identity. This is the exact failure
`tools-over-inference` names: an inference reached him dressed as an observation. The parent PID
was one command away and I did not run it until after the run had already failed.

**10.5 The token gate would have failed the incumbent against itself.** The gate required zero
fence failures outright. Ollama rejected chunk 145 of the Valentine — normal; the analyst's own
reject counter exists for exactly that — so the production backend would have been marked FAIL on
its own numbers. The incumbent sets the bar; a candidate must be no *worse*, not perfect. Found by
reading the arm's output rather than by the gate complaining.
