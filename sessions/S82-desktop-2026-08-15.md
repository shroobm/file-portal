## §6 Results — raising `n` exposed the method instead of confirming the result

### §6.1 What n=30 produced

`Observed` — `backend_parity.py -n 30`, 30 of 266 chunks (stride 8, indices 8–240), qwen3:8b both
sides, warm, concurrency 1, cold-started card. Sample characterisation, computed before the run
finished: sampled median chunk 3,584 chars vs the book's 3,609 — the **median tracks the book
almost exactly**; the upper tail is heavier (p90 4,684 vs 3,996) and the largest chunk (245, at
12,121) is not in the sample. Coverage 11.3 % of chunks, 12.0 % of characters.

**Token gate** — the incumbent sets the bar (2 fence failures, 0 non-stop):

| arm | decode tok | max | not-stop | fence bad | vs ollama | |
|---|---|---|---|---|---|---|
| `ollama think:false` | 20,363 | 900 | 0 | 2 | — | PASS |
| `llama.cpp --jinja` | 90,180 | 7,456 | **1** | 0 | **+342.9 %** | FAIL |
| `llama.cpp +no-think` | 20,346 | 900 | 0 | 1 | **−0.1 %** | PASS |

The `--jinja` arm **hit the cap once** at n=30 — S79's "twice hit the cap" reproducing, on a
sample large enough to catch it. S80's finding holds at n=30 on a fresh sample.

**Throughput, as printed:** ollama prefill 4,519.0 (p50 4,488.4, p95 5,003.0) / decode 100.6
(p50 100.6, p95 103.3); llama.cpp+no-think prefill 2,819.1 (p50 2,793.1, p95 3,216.0) / decode
77.7 (p50 77.3, p95 85.8). Ratios **0.62× prefill, 0.77× decode**. First run to report p95, which
was the point of raising `n`.

### §6.2 Why those ratios are NOT admissible

At n=8 the ratios were 0.81× / 0.95×; at n=30 they are 0.62× / 0.77×. **The gap widened with
sample size**, which reads as confirmation and is the opposite.

`Observed` — regressing decode rate on **position in the run** against **output length**:

| arm | r(length, rate) | r(**position**, rate) |
|---|---|---|
| ollama (1st) | −0.50 | −0.24 |
| llama.cpp default (2nd) | −0.33 | **−0.78** |
| llama.cpp nothink (3rd) | −0.15 | **−0.36** |

The candidates are dominated by **position**, not by how much they wrote. The competing
explanation — decode slows as the KV cache grows — is ruled out: the nothink arm's outputs are
near-constant (mean 678 tokens, and it still declined 4.4 % first-ten to last-ten).

Two independent confirmations:

1. The **same configuration on the same chunks** measured **97.7 tok/s in S81's 7-minute run and
   77.7 tok/s in S82's 25-minute run — −20.5 %**, from run duration alone.
2. A short validation run immediately afterwards measured **Ollama itself** at 71–79 tok/s against
   its own 100–103 on a cool card — so this is **not llama.cpp-specific, it is the card**. The
   harness's own cold-cache calibration fell 2,888 → 1,087 → 823 tok/s across successive runs,
   visible in the instrument's own output.

The arms run in fixed order, so the incumbent is always measured on a cool idle card and the
candidates always on a loaded one. **An A/B where A is always first is not an A/B.** A longer run
means more drift, so the artefact scales with `n` exactly as a real effect would.

**Consequence: the 0.77× / 0.62× ratios are withdrawn as engine comparisons — and so are S81's
0.95× / 0.81×**, which came from the same design and were merely less contaminated by a shorter
run.

### §6.3 The control, built and watched firing

`Observed` — the A-B-A control on a validation run:

```
ORDER DRIFT: incumbent decode 74.8 tok/s first, 88.3 last = +18.1%  GPU 75C -> 83C
*** RATIOS WITHHELD. The incumbent moved +18.1% between its two measurements...
```

The guard was not merely written, it was **watched refusing to publish** on a genuinely unstable
run — the property violated and the alarm heard (docs/32 §5, SKILL.md Phase 4).

### §6.4 The mechanism is NOT what I said it was

I framed the drift as thermal. **The per-request temperature the new control captures contradicts
that**: temperature rose 75 °C → 83 °C while throughput *rose* 74.8 → 88.3 tok/s. Simple thermal
throttling predicts the opposite sign. `nvidia-smi`'s `HW Thermal Slowdown` counter also reads
0 µs lifetime.

So the honest position: **the confound is `Observed` and quantified; its mechanism is `Unknown`.**
Candidates not yet separated — driver/clock boost states settling after a long run, Windows power
management, memory-clock behaviour, or Ollama's engine holding residency differently from a
freshly spawned llama-server. What would resolve it: log clocks and power draw per request across
a controlled idle-then-load sequence.

This distinction matters more than it looks. **The finding stands on the measurement, not on the
story** — every cross-arm ratio is confounded whether or not the cause is heat, because the
incumbent demonstrably moved 18.1 % inside one run.

**What survives:** the **token gate**, which compares output *content* and is order-independent.
`--jinja` alone fails; `enable_thinking:false` restores parity. That conclusion is unaffected.

## §10 Known Failures — mine, first-class

**10.1 I published a confounded ratio, twice, and only caught it because Rab asked for a bigger
sample.** S81's design measured the incumbent first on a cool card and the candidates last on a
hot one, and I reported 0.95× / 0.81× as an engine comparison. The confound was in the design from
the first run; n=8 merely hid it. I wrote the document demanding that conditions be stated
(docs/34 §5) and did not list *measurement order* among them — the one condition that was actually
determining the answer.

**10.2 The worked example in docs/34 §7 was built on it.** I replaced the invented illustration
with "the real S81 measurement" specifically to make the document honest, and thereby put a
confounded number in the position of the document's model of a good number. Corrected.

**10.3 I attached a mechanism I had not measured.** I reported the drift as thermal — to Rab, in
the first draft of `docs/34`, in the manual, and in SYM-035's root-cause column. The per-request
temperature I added *to catch it* then contradicted it: temperature rose while throughput rose,
and `HW Thermal Slowdown` reads 0 µs lifetime. The confound is real and quantified; the mechanism
is `Unknown`. This is `tools-over-inference` again in the same session as §10.1 — a plausible
story travelling as an observation because it explained the data I already had.

**10.4 The prefill guard I built in S81 fired on legitimate measurements.** On the validation run
its cold-cache reference came back at **823 tok/s** — the warmup itself was the anomaly, taken on
a card in an unusual state — so two normal prefills at 3,093 and 3,285 tok/s were withheld as
"cache-contaminated." **The reference is a single measurement**, which is precisely what `docs/34`
rule 3 says never to trust. The fix is specified and not yet built: judge outliers against the
**median of the arm's own prefill rates** (robust to a bad warmup) while keeping the cold-start as
the structural defence against wholesale contamination. Recorded rather than rushed, because
changing a guard needs its own validation run.

**10.5 A layout probe returned nonsense and I nearly read it.** Checking table overflow in the
manual, every `clientWidth` came back **0** because the preview pane was not compositing, making
`scrollWidth > clientWidth` trivially true for all seven wrappers. That is a failed probe, not a
finding (SYM-031). Reported as `UNREAD`; the structural guarantee — every table inside a `.tw`
wrapper with `overflow-x: auto`, measured 868 = 868 when the pane *was* laid out — is what can
honestly be asserted.
