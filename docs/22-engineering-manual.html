File Portal: the complete engineering manual

Two machines, one factory: a Windows desktop with the GPU and the glass, a Linux laptop with the vault and the last word. This manual is written on the car-manual principle — everything the system does, every lever, every file format, every known failure, and why each part is shaped the way it is. Where a fact was verified against source it cites the file; nothing here is folklore.

The laws — invariants that hold everywhere

Every one of these was paid for by a live failure (session numbers in parentheses). They are not style preferences; violating any of them re-opens a closed defect class.

lawstatementorigin
Atomic publishNothing is ever written in place at its final name. Every hop assembles under a dot-prefixed temp (.part-*) and publishes by same-filesystem rename: the widget's transfer, both converters' bundles, slice results, the exporter's vault copy, the remote ship.W1
Single writerEvery state file has exactly one writing process. Two streams that need merging (events.jsonl + receipts) stay two files and merge only at render time. The widget's receipts cache is its own dot-file, never Python's.docs/20 §12
Projection lawThe widget READS; Python owns pipeline truth. UI "controls" only write the backend's own lever files (analyst-mode.txt, audit-mode.txt, chunk-batch.txt…) or spawn its own CLI paths. The Room/Wall/Dock invent no numbers.docs/16 §1
One authority per factNever derive the same number in two languages. Python computes the estimate; line.rs projects it verbatim. Python decides re-analyze eligibility; the Rust click only validates its own action.docs/18 blind spot #1
Telemetry never costs the lineProgress files, events, receipts, ledger records are all best-effort with swallowed failures. A conversion is never lost to its own bookkeeping.S42
Fail-closed on the vault, fail-open on the beltThe exporter refuses when unsure (staging kept, retry on next sweep). Enforcement/provenance on the desktop fails open — losing a bundle is worse than shipping one with a verdict attached.L12 / docs/15 §8
Kill trees, not pidsproc.kill() on Windows kills only the venv launcher; the real python keeps the GPU. Always taskkill /pid N /t /f (_kill_tree), and child processes get a kill-on-close Job Object so no widget exit can orphan them.S48/S52, S37
Liveness is proven, never rememberedProgress files carry mtime as heartbeat; stale claims are ignored (analyst >300s, estimate only while the lock names the same book). The watcher's state is re-polled every 5 s; a death files a certificate (exit code) before reaping.S45–S50

CH·03

Transport — how bytes cross the tailnet

Source: windows-widget/src-tauri/src/transfer.rs (168 lines).

No rsync, no scp. rsync isn't on stock Windows, and plain ssh/scp cannot verify Tailscale SSH's managed host keys — only the tailscale ssh wrapper can. So the transfer is one command, streaming the file's bytes through stdin:

tailscale ssh user@host "mkdir -p <dir> && cat > <dir>/.part-<name> && mv -f .part-<name> <name>"
  • No -- separator and no sh -c: tailscale ssh joins trailing argv with spaces and hands it to the remote login shell; wrapping it double-parses and breaks (comment at transfer.rs:133, confirmed live).
  • Quoting: remote_path_expr leaves a leading ~/ bare (tilde only expands unquoted) and single-quotes the rest, so spaced/quoted filenames survive.
  • Streaming: std::io::copy from disk to the child's stdin — a large drop never loads into RAM.
  • The dot-temp + mv -f is what makes the allocator's event model sound: the watcher sees one on_moved, never a half-written file.

One category never crosses the network: convert-gpu copies into the Desktop's own drop/ (dotfile-then-rename, collision-suffixed) to feed the local conveyor.

The reverse channel is the same transport: status.rs cats logs/status.json; receipts.rs tails receipts.jsonl; the vault clone's git rides core.sshCommand="tailscale ssh"; the bundle ship is tar -cf - | tailscale ssh "tar -xf -" into a .part- dir with the visible (possibly CJK) name applied by the remote mv — Windows bsdtar mangles non-ASCII argv, so tar only ever sees ASCII paths.

CH·04

The allocator — linux-receiver

Source: allocator/main.py (218), rules.py (74), status.py (66), config.py (31). Service: file-portal-allocator. Tests: 24.

Event model — the part that looks wrong until you know why

  • on_moved — a rename into place (the widget's mv -f, rsync). The completion signal.
  • on_closed — inotify IN_CLOSE_WRITE: in-place writers (scp, cp) finished.
  • on_created — only armed when the observer isn't inotify (_observer_emits_close_events); then a size-stability wait (0.5 s poll, 60 s cap) guards against half-written files.
  • Dotfiles skipped; files under quarantine/ skipped (it lives outside the watched tree — the L1 fix for the old re-processing loop); a per-file try/except so one bad file can't kill the observer thread.

Routing

rules.toml is re-read on every event — edits need no restart. Category = the parent directory name. First glob match wins; unmatched → sorted/misc. Templates expand {yyyy}/{mm}/{dd} in local time deliberately (folders a human browses must match the day he dropped the file — guarded with a comment + noqa: DTZ005; do not "fix" with UTC). Oversize (> max_file_size_mb, default 2048) → quarantine + rejected. Collision policy rename (default, " (n)" suffix) / overwrite / skip.

Semantics that surprise: rejected means quarantined, nothing else. An unmatched extension is still allocated (to misc). A red ✗ on the widget = quarantine.

The status feed

logs/status.json: bounded (200 events), rewritten atomically (temp + os.replace). Both the allocator and the converter write it; the read-append-replace cycle is deliberately unlocked — a same-instant collision can drop one advisory UI event, and that narrow race is accepted (log files are the record).

CH·05

The desktop conveyor — windows-converter

Source: watch_and_convert.py (126), convert_and_ship.py (1,193), events.py (28). Runs in the marker-env interpreter; no test suite — verified by live acceptance runs (a fact, not an oversight; see CH·15 SYM-001 for why a stub harness once lied).

The watcher

Poll loop (5 s) over drop/: dotfiles and non-PDFs skipped, size-stability wait (1 s / 120 s), strictly one conversion at a time (the single-flight guarantee on a 10 GB card). Writes .gpu-lock = the converting filename for the duration; success → drop/done/, failure → drop/failed/. The outer subprocess cap is 21,600 s and must stay above the converter's own page-scaled cap or it silently becomes the real limit (S45's unconvertible long books). Analyst routing comes from analyst-mode.txt (off|local|gemini|ask), re-read per file.

convert() — probe, route, run

  1. Consume the ⟳ supersede marker first (drop/.supersede/<name>.json): read-and-delete before any work, so an intent can never outlive its click and latch onto a later same-name drop. Losing one is the safe direction (exporter dedup-skips; Rab clicks again).
  2. Probe (probe()): chars/page, page count, and whether the text layer is an OCR overlay — majority of get_texttrace spans with render type 3 (invisible), plus a glyphless/OCR font-name check. Page counts come from the probe, never PDF metadata ("which lies").
  3. Route (route()): ≥100 chars/page + OCR fonts → --strip_existing_ocr, scan lane, untrusted_ocr_layer; ≥100 clean → clean lane; else scan/no_text_layer. Every lane caps --recognition_batch_size 32: uncapped, Marker auto-scales its batch to fill VRAM and a figure-dense book thrashes to a timeout (the Cybernetics 91-pp DNF).
  4. Promise: estimate_from_ledger() — same lane, 3 nearest neighbors by chars/page, median s/page — written once to .convert-estimate.json and emitted on the probe event. No evidence → basis: "none", the glass says so instead of guessing.

_run_marker() — one implementation of every hard-won lesson

  • A daemon reader thread drains stdout even when broken — a dead reader lets the 64 KB pipe fill and Marker blocks mid-write at zero CPU (S48's cp1252 deadlock, which wore a VRAM costume in S45).
  • tqdm lines are parsed into .convert-progress.json (stage, %, n/total) — the Room's live stage row, and the stall monitor's heartbeat: progress-file mtime frozen > 900 s while the process lives = the stall signature of both wedge species → tree-kill early, emit convert/stalled with a GPU signature (util + VRAM at death, facts only).
  • Hard timeout scales with work: max(3600, pages × 20) s — ~2.5× the worst rate ever measured (8.08 s/pp), so long books are never punished for length.
  • Peak VRAM is sampled in the same wait loop (one watcher, not two).

Chunking — Stage D, spec signed S57

threshold
clean > 600 pp · scan > 400 pp (lanes cost different VRAM); unknown lane takes the stricter bar
slice
200 pages, clean cuts, no overlap — overlap reconciliation risks silent text loss, so seams are recorded (manifest.chunking.seams, 1-based first-pages) rather than smoothed
resume
finished slices publish to .chunk-work/<sha16>/slice-<start>-<end>/ (dot-dir-then-rename, .done written last with wall_s) — outside the temp dir so resume survives the process. A kill or power cut costs one slice. Cleaned after merge (gigabytes).
batch
chunk-batch.txt ∈ {8, 16, 32}, default 16, re-read per slice (a live lever). S60 measured batch 16 peaking 9,786/10,240 MiB — 8 is the headroom setting.
asset numbering
Measured, not assumed: under --page_range Marker numbers assets by ABSOLUTE source page, so slices never collide and nothing is renumbered. out_of_range_assets() is a tripwire that yells if a future Marker changes this — because the first cut assumed run-relative numbering, double-counted the offset, and produced page numbers up to 2553 on a 1,356-pp book (SYM-002).
ledger honesty
resumed slices' prior wall time is folded back into the ledger's wall_s (with run_wall_s + resumed_slices kept beside it) — otherwise every retry teaches the estimator to flatter itself (1.69 vs 1.94 s/pp on Damodaran).

After Marker: bundle → audit → gate → ship

The bundle contract is byte-compatible with the Linux converter's (name clamp 80 utf-8 bytes, ![[assets/…]] link rewrite, same frontmatter and manifest keys), so the ThinkPad exporter needed zero changes. The convert-phase audit runs before any analyst (the witness scores raw Marker output); a conversion ledger record is filed; then routing: --analyst runs it inline, --defer-analyst parks a card in pending/<sha16>/ (unless the auto_local_over_chunks rule auto-routes), --resume ID is the widget's decision, --reanalyze SOURCE is the ⟲ analyst-only re-run (Marker never runs; refuses out loud when only analyst output survives — re-analyzing an analyst pass compounds its damage).

_enforce_hold(): only in audit-mode.txt = enforce, only on verdict fail, park to held/<sha16>/ instead of shipping. S65 guard: an occupant carrying manifest.repairs or a .bench-bak is never rmtree'd — the incoming copy parks beside it, timestamped. Fails open: any error ships rather than loses.

ship(): tar the ASCII .part-<sha16> dir through tailscale ssh into a remote .part-, remote mv to the visible name. If ssh dies, tar is killed so its timeout can't mask the real network error.

CH·06

The analyst — the link-fenced LLM pass

Source: windows-converter/analyst.py (438). Prompt programs live one-per-file in prompts/ (default readability) — retasking is editing a text file, versioned in git.

The fence — the non-negotiable

qwen3:8b once invented image URLs. So every embed (![[…]] and inline) is swapped for an opaque token ⟦IMG-n⟧ before the model sees text, and re-injected verbatim after. A chunk whose token multiset comes back altered is rejected — the original ships un-analyzed. The analyst can improve prose; it can never lose an asset.

Mechanics

chunks
~4,000 chars, split on blank lines, never inside a paragraph; num_ctx 8192
local
Ollama qwen3:8b, think:false, keep_alive:0 (VRAM returns to baseline immediately); called only after Marker exits — the Phase-2 GPU serialization
gemini
Flash via curl, key from env (never disk/logs), temperature 0.2, paced 13 s/request under the free tier's 5 RPM, 429/5xx retried with backoff; docs > ~18 chunks get a "local recommended" warning (the rolling free-tier window, measured live)
resume
S61: every completed chunk is journalled to .analyst-work/<key16>/chunks.jsonl, fsync'd per line. Key binds fenced text + backend + program + chunk size; each record re-validates its input hash; a torn final line is redone. Failed chunks are deliberately NOT journalled — a backend error is transient and must retry, not be remembered. Built the morning a power cut at chunk 936/969 cost 4 hours; the next cut cost ~16 s.
heartbeat
.analyst-progress.json overwritten per chunk; rate measured over chunks generated this run only (resumed chunks would flatter the ETA); deleted on exit so staleness can't lie
ETAs
self-calibrating from analyst/done events (median + p10-slow), static fallback under 3 samples (local 138 chars/s, gemini 186.7 — measured)

Output meta (chunks_passed / rejected / failed / resumed, duration_s) lands in frontmatter and manifest.analyst. preflight() builds the widget card JSON: ETAs both routes, privacy labels ("100% air-gapped" vs "text leaves this machine"), GPU-busy check, recommendation.

CH·07

The Survival Audit — fidelity_audit.py

Source: windows-converter/fidelity_audit.py (491). Deterministic, CPU-only, witness-based. The question it answers: how much of the source survived into the output?

Algorithm

  1. Witness: ephemeral pymupdf text per page (long-path-safe via \\?\ — pre-L15 vault paths reach 349 chars). Both sides normalized: NFKC, quote/dash folding, de-hyphenation, markdown stripped output-side, repeated headers/footers stripped witness-side (a line on ≥40% of pages), casefold, whitespace collapse.
  2. Windows: 12-word non-overlapping (24-char n-grams for CJK — detected at >30% CJK chars, matched space-free). Each window is sought in the output: exact containment, then anchored rapidfuzz partial_ratio ≥ 90 around the rarest word's occurrences.
  3. Scores: per-page survival (pages < 15 words skipped), window-weighted doc survival, adjacent misses ≥ 2 windows merged into "omission runs" with verbatim excerpts.
  4. Tripwires: degeneration (below); reverse-sample (200 seeded-random output windows sought in the witness — anti-hallucination); garbage rate (vowel-less alpha tokens, scan lane); asset delta vs embedded raster count (informational only).

Degeneration — the disease detector

A loop is BOTH crushed-compressible AND extreme-repetitive: per-paragraph zlib ratio < 0.20 AND max repeated word-trigram ≥ 40 (AND, not OR — dense tables compress too, but their words vary: table max trigram measured 28 vs loop minimum 1,674). Plus a contiguous-repeated-line check (a run of > 20 identical non-blank non-table lines, counting only lines longer than 20 chars — legitimate structure repeats distributed, a stuck decoder repeats contiguously).

The verdict — signed policy, do not widen

Exactly two signals reach fail: degeneration (either lane), and analyst near-exact loss (Marker is a perfect reference: survival < 0.995 or any run ≥ 25 words = a rewrite, not reflow). Everything else — low survival, page flags, omission runs, garbage rate — is a localizer: at most flag. Acceptable books measured 0.76–0.96 survival (legitimate reflow); gating on those would false-fail good work and erode the terracotta signal. Signed by Rab 2026-07-20 (docs/15 §12). Whether a fail parks anything is the separate report ⇄ enforce lever.

CH·08

The Linux converter — linux-converter

Source: converter/main.py (320), engines.py (134), bundle.py (145), config.py (77), status.py (67). Service: file-portal-converter (also hosts the exporter, CH·09). Tests: 51, in CI since S67.

Lane topology — no cycle by construction

Two inboxes under one watch: pipeline/convert-inbox (clean) and pipeline/convert-scan-inbox (scan/forced). Clean probes chars/page; below min_chars_per_page (100, provisional) it reroutes to scan as a normal allocated event — a missing text layer is a detectable precondition, not a failure. Scan is terminal: OCR yield below threshold quarantines with rejected. Clean→Scan→nothing; no retry counter needed.

Three load-bearing traps (documented in source, verified live)

  • The hop arrives as created (main.py:11-16): the allocator's rename comes from outside the watch, so inotify reports an unpaired IN_MOVED_TO as plain created — never moved, never close_write. All three handlers are armed; a cp's duplicate event self-cancels because success consumes the source file.
  • Import order is load-bearing (engines.py:7-12): pymupdf.layout must import before pymupdf4llm, which decides at import time whether layout mode (and OCR params) exist.
  • force_ocr=True means FORCE_KEEP_OLD — it would keep a bad prior OCR layer. The scan lane's honest spelling is use_ocr=OCRMode.FORCE_DROP_OLD + ocr_dpi; clean uses SELECT_KEEP_OLD (OCR is need-based and automatic in every mode).

Bundle assembly (shared contract with the desktop)

Assembly dir keyed on source sha (.part-<sha16>), never the stem — pymupdf4llm sanitizes spaces to underscores across directory components (L13: every spaced filename with an image used to quarantine on ENOENT). The engine converts from a short slugified hardlink (≤40 chars) because it derives asset names from the input stem (L15: raw ~230-byte stems blew Windows MAX_PATH on the consuming end). Name clamp: 80 utf-8 bytes, codepoint-safe → worst vault-relative path exactly 160 bytes. publish(): staging gets a copy renamed in, anchor gets the temp dir renamed in — both atomic. Anchor = immutable as-converted snapshot; staging = the export queue. .docx goes through pandoc → gfm (Obsidian reads gfm; media flattened into assets/).

CH·09

The exporter & the vault — the most dangerous module

Source: linux-converter/converter/exporter.py (524). All vault work serialized behind one lock; a startup sweep retries whatever landed while the service was down (started after the watch so nothing lands unseen; export is idempotent).

Git topology

~/file-portal/vault.git      bare, branch main — THE authoritative vault
~/file-portal/vault-work     working clone, origin = the bare repo (the exporter's pen)
Desktop: Obsidian vault/Library   clone of the bare repo over tailscale ssh (read + filing moves)

The exporter never initializes or repairs either repo (exactly one side initializes — that already happened, manually). Notes land at Inbox/<slug60>--<sha8>/ (repo root is the vault's Library folder — L14's doubled-path lesson). The exporter copies bundle bytes; it never reads notes, mints links, or maps folders.

The create path, invariant by invariant

  1. fetch + merge --ff-only — commit on top of the Desktop's filing moves, never behind them.
  2. Dedup on the full source sha, greppd over committed manifest.json in the bare repo — a note the Desktop filed out of Inbox/ still counts (the manifest travels with it). Hit → no-op, staging removed.
  3. Resume-aware copy: committed content is never touched; an uncommitted stray from a failed run is cleaned; .part- assemble → rename → pathspec-scoped commit under a machine identity (file-portal-converter).
  4. Push, then the L12 deletion gate: cat-file -e the commit AND every bundle file's blob in the bare repo. Only then is staging deleted. Any git failure = EXPORT-FAIL, staging kept, retried next sweep.

Supersede — the one exception to create-only

A manifest with an opt-in supersede block (authored only by the widget's ⟳/⟲ clicks) may replace a vaulted note in place. The guard is signed and fail-closed: incoming verdict must be pass, or flag with a valid bless.json (sha-bound, verdict-checked — a degeneration fail can never be blessed from either side). A missing fidelity block is not "pass". The live note is located by sha-grep in the bare repo (never a recomputed path); >1 match refuses; 0 matches falls through to a normal create. Replacement preserves identity — the old .md filename and folder stay (a rename would break wikilinks); assets fully swapped; byte-identical remedies are a no-op that mints no empty commit; commit-without-push resumes by re-push, never re-commit. Outcomes: exported-supersede / supersede-held / supersede-miss / supersede-noop.

Receipts — the seam

Every EXPORT-* outcome appends one JSON line to ~/file-portal/receipts.jsonl (best-effort, never costs an export). This is the vault's side of the story the Desktop could never see — the widget tails it over ssh into its own cache (CH·10). Deliberately a plain file, not vault commits: the vault holds notes, not machine records.

CH·10

The widget — four surfaces, one truth

Source: 14 Rust modules (3,792 lines), main.js (1,025), room.js (871), styles.css (728). Tauri v2, framework-free JS by rule, global Tauri API (no bundler). 20 Rust unit tests. Surfaces: Dock (compact, auto-sized), Room (ops dashboard), Wall (across-the-room), Bench (own window, CH·11).

The Repair Bench — the human is the vision model

Source: prototypes/repair-bench/bench.py (678), bench.html (876), acceptance.py (26 checks against a sandbox of the real Valentine). What it does

The audit says where a conversion went wrong; only a human can see what the page really held. The bench puts the source-PDF page and the markdown at the flagged zone side by side. The repair is one gesture: drag a rectangle (server crops at 220 dpi) or Ctrl+V a screenshot → PNG lands in assets/_repair_pN_k.png (collision-safe), embedded ![[assets/…]] at the zone with an HTML-comment caption, provenance appended to manifest.repairs. First write of a session backs up the .md as .bench-bak.

The clever parts

  • Zone location by evidence (locate_zone): the zone line itself is junk, but surrounding prose is real — 5-word shingles mined from nearby clean lines (window widens 10→25→45 until enough prose), sought in the lazy per-page text index, pages vote. Falls back to the ratio guess and says so. 9/10 of Damodaran's zones located, corrections up to ~39 pages.
  • Line arithmetic has one authority: the server computes adjusted_line (each prior repair inserted 3 lines; each AI edit contributes its drift) — the UI never re-derives it.
  • AI assist (/api/assist): local qwen3 only (Gemini off by standing rule), the analyst's exact contract, under the same link-fence — a reply that damages the token multiset is refused, never patched. Every applied change is one /api/undo from gone (20-deep body snapshots, byte-identical restore). An unchanged reply is an honest no-op that burns no undo slot.
  • Reader mode: the ◆ picker (server-enumerated: held/pending/anchor/done-PDFs — the browser can never hand it a path; open_target is allowlist-contained) opens bundles repairably and bare PDFs read-only with every write path refusing. Okular-grade reading: TOC, normalized full-text search (de-hyphenated, whitespace-joined — needles missed until that join), highlight rects, thumbnails, no-steal search.
  • Re-score is a preview — it re-runs fidelity_audit.degeneration() on current text but writes no verdict: whether repairs earn audit credit is an unsigned policy that belongs to Rab.
  • The transcribe gesture (S71 — docs/23 built): the crop gains a reading eye. ⌨ read region sends the same 220-dpi crop to granite-docling-258M in its own isolated env (transcribe_worker.py, process-per-request — weights load, the crop is read, the process exits, VRAM returns). DocTags render to markdown by library, never by model; gate receipts ride the proposal (parse · numeric-token Jaccard · exact-window survival vs the clip's witness where a text layer exists); the proposal is editable before insert — the human-as-final-gate made literal — and accept is undo-able, stamped repairs[].mode:"transcribe". Refuses while .gpu-lock is held; every failure falls back to the ✂ image embed (the floor). Calibrated before built (prototypes/docling-calibration/): sparse crops 2–3 s; dense TABLE crops output-bound at ~90 s uncontended (the live G5 zone read) with numeric Jaccard 0.95–1.0 and real table structure emitted; degraded-scan crops can refuse into the ✂ floor (measured, by design); ~650–860 MiB peak; fp16 rejected live (no-EOS degeneration — tree-killed), bf16 pinned; worker cap 360 s.

CH·18

Measurement language — how a number may be stated

Full text: docs/34-measurement-language.md. This chapter is the operator's copy. It binds every measured number this project states — in a closeout, a ledger row, a commit message, or a sentence to Rab. Nothing here is house vocabulary: every term is the term the field already uses, so that one of our numbers and a stranger's benchmark mean the same thing.

Why it exists. S79 measured llama.cpp and wrote "+27 % tok/s and 1.72× batching." At S80's open those numbers could not be used — not because they were wrong, but because the sentence never says what was counted, over which clock, under what conditions. +27 % of which tokens? Input or output? Warm or cold? One request or many? Against which build? A number stated that way is not a measurement; it is a rumour with a decimal point. This is Rab's S79 law — a name must carry a mechanism — applied to quantities.

The five costs inside one request

Almost every misleading benchmark quotes one of these and implies another.

CostWhat is happeningPaid when
1 Loadweights read from disk into VRAMcold start only
2 Prefillinput tokens processed, KV cache builtevery request — scales with input length
3 Decodeoutput tokens produced, one at a timeevery request — scales with output length
4 TransportHTTP, JSON, process hopevery request
5 Queuewaiting behind other requestsunder concurrency only

Prefill and decode have different physics. Prefill is compute-bound and parallel — the whole prompt at once. Decode is memory-bandwidth-bound and sequential — each token waits for the one before it. Prefill routinely runs 3–10× the tokens per second decode does, on the same card and model. A single blended "tok/s" therefore says almost nothing: change the ratio of input length to output length and the blended figure moves while nothing about the machine has.

Observed S81, this card, qwen3:8b, 15-token prompt: prefill 339.6 tok/s, decode 56.1 tok/s — a 6.1× difference inside one request.

throughput is never used bare — it is always prefill throughput or decode throughput. An unqualified "tok/s" is not admissible here. Concurrency is not batch size: concurrency is what the client does, batch size is what the server does about it (S79's "1.72× batching" names neither, which is part of why it cannot be banked). Goodput is the figure that pays the bills on this line: the analyst's output is worth nothing unless it passes the image fence, and a truncated rewrite drops trailing ⟦IMG-n⟧ so the un-analyzed original ships. Tokens produced and then rejected are waste, not throughput.

The rules

  1. Name the numerator and the denominator. "Decode throughput 56.1 tok/s" — output tokens over decode-phase seconds. Not "56 tok/s".
  2. Never mix cold and warm. Load is reported separately or excluded explicitly. A cold first request can be 10× the wall time of the warm ones after it; averaging them describes no real request.
  3. State n and a spread. A bare mean hides its own dispersion. Give p50 and min–max (or p95 once n ≥ 20). One measurement is n=1 and must say so.
  4. A ratio prints both of its sides. Not "1.72× faster" but "1.72× (A 96 tok/s vs B 56 tok/s, both warm decode)".
  5. A percentage prints its base. "+27 %" is meaningless without "of what, measured how".
  6. A rate needs a duration the backend actually reported. Missing field ⇒ UNREAD, never 0.0 tok/s, never a silent fallback to wall time dressed as the model's own clock (SYM-031).
  7. Sampling never promotes. N chunks measured is Inferred about the corpus, never Observed about all of it. Say which, and give N.
  8. A ratio needs two runs. One run's ratio, however well-conditioned, stays inside the instrument's own output; it is published only after a second independent run (a different day, a re-idled card) agrees within the order-drift limit. Added S83 — four ratios were published on one run each, and all four were withdrawn.

Corollary — state the build. A rate belongs to one engine build, model file and card. llama.cpp reports system_fingerprint (e.g. b10448-ad1de39e0); Ollama reports its version. Record it beside the number, or next month's comparison is against an unknown.

⚠ The unit trap. Ollama reports nanoseconds. llama.cpp reports milliseconds. Same shape of number, same position, same kind of response — differing by 10⁶. A rate computed with the wrong divisor is not obviously wrong; it is off by a factor of a million, which reads as either absurd or, after a second mistake, plausible. Convert both to seconds at the boundary, once, and never carry a raw duration further.

⚠ Cached prefill is not measured prefill. Both backends reuse the KV cache across requests sharing a prefix. When cached_tokens/cache_n is non-zero, part of the prefill did not happen and a prefill rate computed over the full prompt is inflated — sometimes enormously. Observed S81: the harness written to obey this document warmed up on a chunk it then measured, and reported 37,729 tok/s prefill against 4,801 for the next chunk — an eightfold "speedup" that was the instrument measuring its own warmup; on the next run its second llama.cpp arm re-sent the first arm's exact prompts and was handed 524 and 1,166 tokens free, reporting prompt_n = 1. Note that timings.prompt_n counts tokens actually processed, not the prompt's length, so a cached prompt yields a rate that is arithmetically correct and describes a one-token prefill.

The rule: a prefill rate is WITHHELD — UNREAD — when more than 20 % of its prompt arrived from cache. Not footnoted, withheld: a number that is correct and materially meaningless is still a lie told to whoever reads it next. Measure so it does not arise — warm on a chunk you will not time, send distinct prompts, and set "cache_prompt": false where the engine allows it — and start from a proven-cold card, unloading the model before the baseline so the cache is empty by construction rather than by hope.

When the cache is invisible. Ollama exposes no cache field at all, so the 20 % rule cannot even be evaluated for it — the guard is blind exactly where the danger is unseeable. Two defences, both needed: unload first (structural), and treat the warmup — which follows a proven-cold card, so its prefill is real — as the run's measured reference for this hardware, withholding any later rate more than 3× it. A measured reference beats a hardcoded ceiling, which would rot the first time the card changes. Observed S81, the third instance in one session: with a previous run's engine still resident, Ollama reported prefill at 61,093 / 63,619 / 65,393 tok/s on a card whose honest figure is ~4,000–6,000, and the same run printed a VRAM “baseline” of 7,323 MiB taken while a model was loaded — which would have made its own unload check pass trivially. Neither raised an error. These paragraphs exist because writing the warning down was not sufficient to avoid the thing warned about.

The independent second clock. Both tables are the server's own account of itself, so two rates drawn from them are one check (SYM-001). The harness also records client-side wall time — a differently-shaped measurement including transport, which cannot be wrong the same way. Server phases must total less than wall time; if they ever exceed it, the unit mapping is wrong, and that discrepancy is the alarm.

Measurement order is a condition

An A/B in which A is always measured first and B always second is not an A/B. Hardware does not hold still across a long run, and whichever arm runs last is measured — in effect — on a different machine than the one that ran first.

Do not attach a mechanism you have not measured. S82 first framed this as thermal throttling; the per-request temperature added to catch it then showed temperature rising 75 °C → 83 °C while throughput also rose 74.8 → 88.3 tok/s — the wrong sign for simple throttling — and HW Thermal Slowdown reads 0 µs lifetime. The confound is Observed and quantified; its mechanism is Unknown. That is enough: the finding rests on the measured drift, not on the story.

Observed S82 three arms, fixed order, n=30 over ~25 minutes. Decode rate regressed on position in the run versus on output length:

armr(length, rate)r(position, rate)
ollama (1st)−0.50−0.24
llama.cpp default (2nd)−0.33−0.78
llama.cpp nothink (3rd)−0.15−0.36

The candidates are dominated by position, not by how much they wrote — and the nothink arm's outputs are near-constant (mean 678 tokens), so length cannot explain its decline. The decisive comparison: the same configuration on the same chunks measured 97.7 tok/s in a 7-minute run and 77.7 tok/s in a 25-minute one — −20.5 %, from run duration alone.

The rule: measure the incumbent twice — first and last (A-B-A) — and publish the drift. If the incumbent moves more than 5 % between its own two measurements, the card did not hold still and cross-arm ratios are withheld: they would report the run's own drift as an engine difference. Sample GPU temperature and clock per request so the mechanism is visible rather than inferred. Interleaving arms request-by-request is the stronger control but is unavailable here — it needs both backends resident at once, which SYM-022 forbids. A-B-A is what the one-process-on-the-card law leaves available.

Name the invocation, not just the product

Observed S81 Ollama 0.32.13 runs llama-server as its own inference engine (AppData\Local\Programs\Ollama\lib\ollama\llama-server.exe, spawned by ollama serve). So a measurement labelled “Ollama vs llama.cpp” is not engine versus engine — it is one engine under two sets of flags:

A smaller micro-batch processes the prompt in more passes, which was the leading candidate for the prefill gap — back when a prefill gap was still a measured quantity. S82 withdrew those ratios (see the worked example below). The flags question survives the withdrawal and is now the only live one, because it asks about a single engine rather than comparing two runs. State the flags whenever the engines are named, or a configuration difference gets reported as an engine difference.

A worked example

Not admissible:

llama.cpp is 27% faster.

Which tokens? Which phase? Warm? How many requests? Which build? Nothing can be checked, and nothing can be re-derived once anything changes.

Admissible:

Token gate, n=30, 30 of 266 chunks, qwen3:8b both sides:
  llama.cpp --jinja                 90,180 decode tok  (+342.9% vs incumbent, hit the cap once)
  llama.cpp --jinja +no-think       20,346 decode tok  (-0.1%, 0 non-stop, fence no worse)
  ollama 0.32.13 (incumbent)        20,363 decode tok
ollama 0.32.13, llama.cpp b10448-ad1de39e0, RTX 3080, -c 8192, flash-attn on.
30 of 266 chunks - Inferred about the book.
Reproduce: python windows-converter/backend_parity.py -n 30

Why this example is a token gate and not a throughput number. This chapter previously carried “llama.cpp 0.95× decode, 0.81× prefill” here as the model of a well-stated number. Those ratios have been withdrawn, along with the n=30 figures that appeared to confirm them (0.77× and 0.62×): they were confounded by measurement order, and raising n made the artefact larger, which looked like corroboration.

It is recorded rather than deleted because it is the sharpest lesson here: a number can satisfy every rule in this chapter — numerator, denominator, n, spread, build, conditions, a reproducing command — and still be wrong, because the conditions list was missing an entry nobody had thought of. The rules make a number checkable. They do not make it true. The example above compares output content, which is order-independent, so it survived the failure that destroyed the throughput figures.

The second is longer. It is also the only one worth writing down, because it is the only one still checkable in six months by someone who was not there.

Where this is enforced. windows-converter/backend_parity.py prints in this vocabulary and refuses to print a rate whose duration it did not observe. If the harness and docs/34 ever disagree, the harness is wrong — a document may describe an instrument, but an instrument may not invent a word the document does not define. docs/21 supplies the epistemic tag; this chapter supplies the units. A number needs both: what kind of claim it is, and what it counts.

What this cannot do: it cannot make a measurement correct — only legible and checkable. A number can satisfy every rule here and still be measured on the wrong workload, which is the mistake this project has made most often. Legibility is the floor, not the proof.
